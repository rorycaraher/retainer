# Audio Note recordings stored as immutable SQLite BLOBs, no transcoding

Audio Notes (a new Note kind alongside Text Note and Checklist) store their recording as a BLOB column in the same SQLite database as everything else, rather than as files on disk or in an external object store like Cloudflare R2. This preserves the "one file, trivial backup" property from ADR 0003 that motivated SQLite in the first place — a second storage location (filesystem or a cloud bucket) would mean two things to back up in sync, a new orphaned-file/orphaned-row failure mode, and for R2 specifically, a network dependency and third-party account that this self-hosted, single-user app doesn't otherwise need. A capped recording length (5 minutes, enforced both client- and server-side) keeps the size cost of this choice bounded.

Recordings are stored in whatever format the browser's `MediaRecorder` natively produces (e.g. WebM/Opus in Chrome/Firefox, MP4/AAC in Safari) rather than transcoded server-side to a single canonical format. Normalizing would require adding `ffmpeg` (or similar) as a backend dependency; since v1 playback is browser-only, the browser that recorded a clip can always play it back, so cross-format compatibility is deferred until a client that didn't record the clip (e.g. a future native mobile app) needs to play it.

An Audio Note's recording is immutable once saved — there's no in-place re-record or edit, only delete-and-create-a-new-one. This sidesteps inventing a merge rule for concurrent binary edits: ADR 0001's field-level HLC merge works because every field is either untouched or resolvable by last-write-wins for that single field; audio has no meaningful way to merge two different recordings, so avoiding mutation entirely keeps the existing sync model sufficient without a special case.
